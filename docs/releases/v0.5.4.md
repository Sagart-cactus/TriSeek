# TriSeek v0.5.4

v0.5.4 is a memory stability release for MCP file discovery on very large roots.

## Highlights

- Fixed MCP `find_files` memory growth when TriSeek falls back to direct path search on large roots.
- Added metadata-only direct path scanning so filename discovery no longer reads and retains every file body.
- Kept content search behavior unchanged: direct content scans still read file bodies when they need to verify matches.
- Added a regression test proving direct path search does not read unreadable file contents.

## Root Cause

When TriSeek avoided a memory-risk legacy index, MCP `find_files` fell back to direct path search. That fallback used the full repository scanner, which reads file contents for indexing and content search. Path-only search only needs metadata, but on large roots this retained many file bodies unnecessarily.

On a large `/Users/trivedi/Documents/Projects` root, this meant a filename query could scan roughly 196k searchable files and about 2.3 GB of searchable content.

## Migration Notes

No data migration is required. Restart long-running MCP server or daemon processes after upgrading so they use the new binaries.

## Validation

- `cargo fmt`
- `cargo test -p search-index`
- `cargo test -p triseek find_files`
- `cargo test -p triseek non_indexed_fallback_bypasses_cache`
- `cargo build --release -p triseek -p search-server`
- Installed-binary repro on `/Users/trivedi/Documents/Projects`: MCP `find_files` stayed under about 46 MB RSS and returned normally.
