# TriSeek v0.4.3

v0.4.3 is a maintenance release focused on daemon memory behavior and docs polish.

## Highlights

- Fixed daemon RSS growth during repeated RPC workloads with large JSON payloads.
- Replaced one-thread-per-connection handling with a single long-lived connection worker.
- Removed the in-memory session action-log cache; action entries remain append-only on disk and are read on demand for status and snapshots.
- Improved responsive docs navigation and table wrapping across the static HTML pages.

## Root Cause

The daemon accepted each loopback TCP RPC connection and spawned a fresh OS thread to process it. Under repeated MCP calls with large payloads, process RSS grew because each short-lived connection thread allocated and freed large JSON buffers, and the allocator retained that memory at process level.

The session store also duplicated action payloads in memory even though they were already persisted to `action_log.jsonl`.

## Fix Details

- `triseek-server` now queues accepted connections to a long-lived worker thread.
- `SessionStore` no longer keeps a process-wide `Vec<ActionLogEntry>`.
- `session_status` and snapshot creation read a session's persisted action log when needed.
- Existing action-log file formats and MCP response shapes are unchanged.

## Migration Notes

No migration is required. Existing daemon session and snapshot files remain compatible.

After upgrading, restart the daemon so the new server process is active:

```sh
triseek daemon restart
```

The installers already stop and restart the daemon during reinstall.

## Validation

- `cargo fmt --check`
- `git diff --check`
- `cargo test`
- Runtime RSS stress probe, 4,000 `session_record_action` RPCs with 4 KiB payloads:
  - pre-fix: RSS +21,744 KiB total, +10,452 KiB in the second half
  - v0.4.3 fix: RSS +1,296 KiB total, +108 KiB in the second half
- CI smoke builds on Linux, macOS, and Windows
